### 테스트를 왜 하는가? 
프로그래밍의 근본은 **"목표한 기능이 잘 동작하는가"** 입니다. 테스트 코드는 그런 의미에서 굉장히 중요합니다. 내 코드가 잘 동작 하는지 확인할 수 있는 가장 쉬운 방법이기 때문입니다. 

-단위 테스트는 **각 모듈이나 함수가 독립적으로 올바르게 동작하는지**를 확인하는 작업입니다. 이를 통해 코드 결합에 의한 문제를 **사전에 방지**할 수 있으며, 프로젝트 규모가 커질수록 **빠르게 오류를 발견하고 수정**할 수 있는 핵심적인 도구가 됩니다. 프로젝트가 커질수록 아 단위 테스트의 역할을 굉장히 중요해 집니다. 모든 코드가 잘 동작한다는 것을 그 무엇보다 빠르게 확인할 수 있기 때문입니다. 

테스트 코드를 작성하는 것은 굉장히 귀찮은 일입니다. 더군다나 작은 프로젝트를 구성할 때는 더더욱 그렇게 생각하기 쉽습니다. 동작 여부를 직접 확인할 수 있기 때문입니다. 하지만 프로젝트가 커지는 것을 필연적이며 개발자는 반드시 미래를 염두해두고 코딩을 해야 합니다. 

### 좋은 테스트 코드란?
독립적이고, 가독성이 좋은 코드가 좋은 테스트 코드라고 생각합니다. 테스트 간 의존성을 최대한 줄이는 것이 좋습니다. 
또한 신뢰성 높은 테스트 코드를 작성해야 합니다. 놓친 부분을 빠르게 파악할 수 있어야 하기 때문입니다. 

테스트 코드는 속도가 중요합니다. 수 없이 발생하는 CI/CD 환경에서 테스트 코드가 느리다면 배포에 큰 문제가 생길 수 있습니다. 그런 점에서 `@SpringBootTest`를 사용하는 것을 고려해볼 필요가 있습니다. 

`@SpringBootTest`는 **통합 테스트**를 할 때 유용하지만, 모든 테스트에서 사용하기에는 무거울 수 있습니다. **단위 테스트**에서는 가벼운 테스트 도구인 **`@WebMvcTest`**, `Mockito`, 또는 **`@MockBean`** 등을 활용하여 빠르게 테스트를 진행하는 것이 좋습니다. **통합 테스트**는 애플리케이션 전반의 흐름을 검증할 때 사용하고, **단위 테스트**는 빠르고 독립적으로 각 모듈을 검증하는 데 초점을 맞춰야 합니다.

이 외에도 테스트 코드는 **일관된 결과를 보장하는 멱등성**을 가져야 합니다. 동일한 테스트가 **여러 번 실행되어도 동일한 결과**를 내야 하며, 테스트 환경에 의존하지 않도록 **테스트 간 의존성을 제거**하는 것이 중요합니다. 특히, 외부 API를 호출하거나 동시성 이슈를 다루는 경우 멱등성이 테스트 코드의 신뢰성을 보장하는 중요한 요소가 됩니다.

### @BeforeEach 어노테이션의 장단점

`@BeforeEach`는 JUnit 프레임워크에서 각 테스트 메서드가 실행되기 전에 **매번 실행**되는 메서드를 지정하는 어노테이션입니다. 이를 통해 **테스트 코드의 초기화 작업**을 수행하며, 테스트 메서드 간 중복된 설정 코드를 제거하여 **코드의 간결성**과 **유지보수성**을 높일 수 있습니다. 하지만, 단점도 존재합니다. 

**장점**
1. **중복 코드 제거**
   - 각각의 테스트 메서드에서 반복되는 설정 코드를 중복으로 작성할 필요 없이, `@BeforeEach`로 **한 번만 작성**하면 됩니다. 이를 통해 **코드의 중복을 줄이고 유지보수성**을 높일 수 있습니다.

2. **테스트 코드의 가독성 향상**
   - 설정 코드를 각 테스트 메서드 안에 포함하지 않으므로, **테스트 메서드의 목적**이 더 명확해지고 **가독성**이 향상됩니다. 테스트 메서드는 오직 **테스트 목적에만 집중**할 수 있게 됩니다.

3. **테스트의 독립성 보장**
   - 각 테스트 메서드가 독립적으로 실행되며, 테스트 간의 **의존성을 최소화**할 수 있습니다. 이는 테스트 순서에 영향을 받지 않고도 **테스트의 신뢰성**을 높여줍니다.

4. **유지보수 용이성**
   - 초기화 코드가 **하나의 메서드에 집중**되기 때문에, 초기화 로직에 변경이 필요할 경우 해당 메서드만 수정하면 됩니다. 이로 인해 **유지보수가 쉬워지고**, 초기화 코드 관리가 더 간편해집니다.

5. **테스트 유연성 증가**
   - **각 테스트가 독립적**으로 실행되므로, 테스트 순서에 관계없이 각 테스트가 원하는 환경에서 잘 실행될 수 있습니다.

**단점**
1. **테스트 간 의존성 증가 가능성**
   - `@BeforeEach`를 **남용**하거나 설정이 복잡해지면, 테스트 간의 **의존성이 증가**할 수 있습니다. 이로 인해 테스트의 **격리성이 감소**하여 테스트 결과에 영향을 줄 수 있습니다.

2. **테스트 실행 시간 증가**
   - 각 테스트 메서드가 실행되기 전에 초기화 코드가 실행되므로, **복잡한 초기화 작업**이 많거나 **리소스를 많이 소모하는 경우** 테스트 실행 시간이 증가할 수 있습니다. 특히 테스트가 많아질수록 **초기화 작업**이 반복되어 성능에 영향을 미칠 수 있습니다.

3. **초기화 메서드의 오용**
   - 모든 테스트가 같은 초기화 메서드를 실행하기 때문에, 특정 테스트에 맞게 설정 코드를 변경하면 다른 테스트 케이스에 **의도치 않은 영향을 줄 수 있습니다**. 설정이 테스트 간에 **결합도를 높일** 위험이 존재합니다.

4. **테스트 의도 모호성**
   - 초기화 로직이 테스트 메서드에서 멀리 떨어져 있기 때문에, **테스트가 무엇을 검증하는지 바로 이해하기 어려울 수 있습니다**. 설정 코드를 살펴보지 않으면 **테스트의 기대값을 파악하기 어려운 상황**이 발생할 수 있습니다.

5. **결합된 설정 코드로 인한 복잡성**
   - `@BeforeEach` 메서드를 수정하면 **해당 설정 코드에 의존하는 모든 테스트**가 영향을 받을 수 있습니다. 이는 **테스트 코드가 과도하게 결합**되면서 **유연성을 해칠** 수 있습니다.

### 테스트 코드는 내부 구현에 의존하면 안된다 
```java
@Test
void shouldReturnSumOfTwoNumbers() {
    // Given
    Calculator calculator = new Calculator();
    int value1 = 1;
    int value2 = 2;

    // When
    int actual = calculator.add(value1, value2);

	
    // Then
    //assertThat(actual).isEqualTo(value1 + value2) // 내부 구현이 들어남
    assertThat(actual).isEqualTo(3);  // expected 값을 직접적으로 명시
}
```

**테스트의 목적**은 **동작을 검증**하는 것이지, 내부 구현 세부 사항을 테스트하는 것이 아닙니다. 만약 테스트 코드가 내부 구현에 지나치게 의존한다면, **구현 방식이 변경될 때마다** 테스트 코드도 함께 수정해야 하는 문제가 생길 수 있습니다.

테스트 코드를 작성할 때, **내부 구현에 의존하지 않고** 입력값과 출력값에만 초점을 맞추는 것이 좋습니다. **expected 변수를 직접 계산하는 방식**은 테스트가 **내부 로직에 지나치게 의존**할 수 있으며, 이는 테스트의 본질을 훼손할 수 있습니다. 따라서 **기대 결과값을 명시적으로 작성**하는 것이 더 나은 접근 방식입니다.

### 테스트 간 의존성을 최소로 해야한다 
```java
// 나쁜 테스트: 테스트 간 상태를 공유함
List<Integer> sharedList = new ArrayList<>();

@Test
void testAddToList() {
    sharedList.add(1);
    assertThat(sharedList.size()).isEqualTo(1);
}

@Test
void testClearList() {
    sharedList.clear();
    assertThat(sharedList.size()).isEqualTo(0);
}

// 좋은 테스트: 테스트 간 독립성 보장
@Test
void testAddToList() {
    List<Integer> list = new ArrayList<>();
    list.add(1);
    assertThat(list.size()).isEqualTo(1);
}

@Test
void testClearList() {
    List<Integer> list = new ArrayList<>();
    list.add(1);
    list.clear();
    assertThat(list.size()).isEqualTo(0);
}
```

### 외부 요인에 의해 결정되는 경우 목으로 대체
```java
// 나쁜 테스트: 외부 API에 의존하여 비결정적일 수 있음
@Test
void testApiCall() {
    ExternalApi api = new ExternalApi();
    String response = api.getResponse();
    assertThat(response).isEqualTo("Expected Response");
}

// 좋은 테스트: Mock을 사용하여 결정적 테스트
@Test
void testApiCall() {

    when(api.getResponse()).thenReturn("Expected Response");

    assertThat(response).isEqualTo("Expected Response");
}
```

### 테스트 더블이란 
테스트 더블(Test Double)은 실제 객체를 대신하여 테스트의 특정 조건을 만족시키거나 특정 상황을 시뮬레이션하는 데 사용됩니다. 이는 실제 객체를 사용하기 어렵거나 테스트 실행 시간을 단축하기 위한 목적에서 활용됩니다. 테스트 더블에는 주로 스텁(Stub), 모크(Mock), 스파이(Spy), 페이크(Fake) 등이 있습니다.

스텁(Stub)은 호출된 메서드에 대해 미리 정의된 응답을 반환하는 간단한 구현체로, 외부 시스템의 응답을 시뮬레이션할 때 유용합니다. 
```java
public class UserService {
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public String getUserEmail(int userId) {
        return userRepository.findEmailById(userId);
    }
}

public class StubUserRepository implements UserRepository {
    @Override
    public String findEmailById(int userId) {
        return "test@example.com";  // 미리 정의된 값 반환
    }
}

@Test
void testGetUserEmailUsingStub() {
    UserRepository stubRepo = new StubUserRepository();
    UserService userService = new UserService(stubRepo);

    String email = userService.getUserEmail(1);

    assertThat(email).isEqualTo("test@example.com");
}

```

모크(Mock)는 메서드의 호출 여부, 호출 순서, 전달된 파라미터 등을 검증하는 데 사용되며, 주로 객체의 행위를 검증하는 데 효과적입니다. 
```java
@Test
void testGetUserEmailUsingMock() {
    UserRepository mockRepo = mock(UserRepository.class);
    UserService userService = new UserService(mockRepo);

    userService.getUserEmail(1);

    verify(mockRepo).findEmailById(1);  // findEmailById 메서드가 호출되었는지 검증
}

```

스파이(Spy)는 실제 객체의 기능을 그대로 사용하면서도 메서드 호출 정보를 기록해, 함수가 예상대로 동작하는지 확인할 수 있습니다. 
```java
@Test
void testGetUserEmailUsingSpy() {
    UserRepository realRepo = new RealUserRepository();  // 실제 객체
    UserRepository spyRepo = spy(realRepo);  // 스파이 객체 생성
    UserService userService = new UserService(spyRepo);

    userService.getUserEmail(1);

    verify(spyRepo).findEmailById(1);  // 메서드가 호출되었는지 검증
}

```

페이크(Fake)는 실제 동작하는 간소화된 구현체로, 예를 들어 인메모리 데이터베이스를 사용해 실제 데이터베이스 시스템을 시뮬레이션할 수 있습니다.
```java
public class FakeUserRepository implements UserRepository {
    private Map<Integer, String> data = new HashMap<>();

    @Override
    public String findEmailById(int userId) {
        return data.get(userId);  // 인메모리 저장소에서 데이터 조회
    }

    public void saveUser(int userId, String email) {
        data.put(userId, email);  // 인메모리 저장소에 데이터 저장
    }
}

@Test
void testGetUserEmailUsingFake() {
    FakeUserRepository fakeRepo = new FakeUserRepository();
    fakeRepo.saveUser(1, "fake@example.com");  // 테스트를 위한 가짜 데이터 저장
    UserService userService = new UserService(fakeRepo);

    String email = userService.getUserEmail(1);

    assertThat(email).isEqualTo("fake@example.com");
}

```
테스트 더블은 테스트의 복잡성을 줄이고 테스트의 신뢰성을 높이기 위해 사용되며, 실제 객체와 유사하게 보이고 동작하지만 실제로는 더 간단하게 설계된 객체입니다.

### assertJ와 jUnit의 차이 
JUnit은 자바에서 단위 테스트를 위한 **프레임워크**로, 주로 **테스트 흐름을 제어**하고 **테스트 수명 주기**를 관리하는 역할을 합니다. JUnit은 `@Test` 어노테이션을 사용하여 테스트 메서드를 정의하고, **테스트 실행 흐름**을 관리합니다. 또한 `@BeforeEach`, `@AfterEach` 같은 어노테이션을 통해 **테스트 생명 주기**를 제어하며, 기본적인 `assert` 메서드를 제공하여 테스트의 성공 여부를 확인하고 보고하는 기능을 수행합니다.

AssertJ는 **단언문**을 강화하여 보다 **표현력이 뛰어난 테스트 코드**를 작성할 수 있도록 돕는 **라이브러리**입니다. JUnit과 함께 사용되며, 다양한 **assert 문**을 제공하여 코드의 **가독성**과 **명확성**을 높입니다. AssertJ는 **메서드 체이닝**을 지원하여 단언문을 **더 직관적이고 간결하게** 작성할 수 있게 해줍니다. 예를 들어, 객체의 필드 값, 컬렉션의 크기, 예외 발생 여부 등 다양한 상황을 검증할 수 있는 **다양한 검증 메서드**를 제공합니다.

둘은 상호 보완적으로 사용되는 도구입니다. 따라서 함께 사용하는 것이 좋습니다. 

JUnit은 **테스트 실행**을 위한 필수 도구이지만, **기본 제공 `assert` 메서드**는 비교적 제한적이며, 복잡한 검증을 작성할 때 **코드 가독성이 떨어질 수 있습니다**. 예를 들어, 객체 필드나 컬렉션에 대한 세부 검증을 할 때, **AssertJ**가 제공하는 **체인 형태의 직관적인 API**가 더 가독성이 좋고, **테스트 코드를 명확하게 작성할 수 있게** 도와줍니다.

```java
@Test
void testBasicAssertionWithJUnit() {
    int expected = 5;
    int actual = 3 + 2;
    assertEquals(expected, actual);  // JUnit의 기본 assert 메서드
}
```

assertJ를 쓴다면 
```java
@Test
void testAssertionWithAssertJ() {
    int actual = 3 + 2;
    assertThat(actual).isEqualTo(5);  // AssertJ의 체인 메서드를 이용한 더 직관적인 검증
}
```

더 복잡한 검증에서도
```java
@Test
void testListWithAssertJ() {
    List<String> names = Arrays.asList("John", "Jane", "Tom");
    assertThat(names)
        .hasSize(3)                  // 컬렉션 크기 검증
        .contains("John", "Jane")    // 특정 요소 포함 여부 검증
        .doesNotContain("Alex");     // 포함하지 않는 요소 검증
}
```

### 테스트 만을 위한 메소드

**테스트만을 위한 메서드 작성에 대한 원칙**은 **프로덕션 코드의 순수성**을 유지하는 것이 우선입니다. 프로덕션 코드에 테스트만을 위해 불필요한 메서드가 포함되면, **코드 유지보수성**과 **읽기 쉬운 코드 작성** 원칙을 해칠 수 있습니다. **테스트의 목적**은 **프로덕션 코드를 검증**하는 것이지, 프로덕션 코드에 불필요한 책임을 추가하는 것이 아닙니다.

따라서, **테스트만을 위한 메서드 작성은 지양**해야 하며, 아래의 가이드를 따르는 것이 좋습니다:

캡슐화를 깨지 말라.
    객체의 내부 상태나 동작은 **테스트를 위해 노출되지 않아야** 하며, 그 대신 **테스트 가능하게 설계된 인터페이스**를 활용하는 것이 바람직합니다. 예를 들어, 테스트만을 위해 `getter` 메서드를 추가하는 것은 객체의 **캡슐화**를 해칠 수 있으므로 조심해야 합니다. 

테스트가 힘들다면 코드가 잘못 짜여 있을 확률이 높다.
	테스트가 힘들다면, 이는 프로덕션 코드가 **테스트하기 어렵게 설계되었을 가능성**이 있습니다. 이 경우에는 **의존성 주입(DI)** 또는 **리팩토링**을 통해 테스트를 쉽게 할 수 있는 설계를 도입해야 합니다.

다양한 생성자를 활용해라.
    테스트를 위한 **다양한 생성자를 제공**하는 것은 괜찮습니다. 이는 객체를 **유연하게 초기화**할 수 있게 하며, 테스트와 프로덕션 코드 모두에서 이점을 줄 수 있습니다. 다만, **지나치게 많은 생성자를 만들지 않도록** 조심해야 하며, 객체의 생성을 **간소화**하는 방향으로 설계합니다.

테스트 더블을 사용해라.
    프로덕션 코드에 테스트 목적의 메서드를 추가하는 대신, **Mockito**와 같은 라이브러리를 통해 **Mocking**이나 **테스트 더블**을 활용하는 것이 더 좋습니다. 이를 통해 객체의 내부 구현을 테스트하지 않고도 **행위 기반 테스트**를 수행할 수 있습니다.
